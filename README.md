# ResQGo (災害救助支援デリバリーアプリ)
稼働URL: https://gms.gdl.jp/~reosato/disaster-delivery/

サポーターズ・技育CAMPハッカソンにて開発・本番デプロイを完遂した、被災者のリアルタイムなニーズとボランティアの最適な救助経路をマッチングするモバイルアプリケーションです。

## 🚀 プロダクトの核 (Why・How・Fact)

###  【Why】解決する課題
災害発生時における「避難所単位」の大まかな物資配分ではなく、**孤立した被災者個人の「今、水が必要」「持病の薬が足りない」といったピンポイントな微細ニーズが可視化されない**という課題を解決します。リアルタイムに位置情報と紐づいた需要をマップ上にプロットし、動けるボランティアへ最適な救助ルートを提案します。

###  【How】技術選定と開発プロセス
* **Frontend:** Flutter (Dart) によるクロスプラットフォーム開発。タイムクリティカルな状況での直感的なUI/UXを実装。
* **Backend:** Firebase (Firestore / Authentication) を採用し、NoSQLによるリアルタイムなデータ同期基盤を高速に構築。
* **AI-Driven Development:** 限られたハッカソンの時間制限の中で、LLM（大規模言語モデル）を単なるテキストジェネレータではなく**「リアルタイムで並走するペアプログラマー」**として定義。アーキテクチャの壁打ち、Firebaseのセキュリティルール設計、エッジケースの即時デバッグに徹底的に使い倒すことで、開発速度とロジックの安全性を両立させました。

###  【Fact】客観的成果
* 技育CAMPハッカソンにて、限られた時間制限の中でフロントエンドからバックエンドのインフラ統合、および本番環境へのデプロイ（デモ稼働可能な状態）までを完全ワンオペで完遂。

## 🧠 将来のプロダクション化に向けた設計メモ（Architecture & Trade-offs）

本プロダクトは、ハッカソンという極限の時間制約において「動く状態での本番デプロイ」と、被災者がストアを介さずURLのみで即時アクセスできる「Web/PWAの即時性」を最優先に設計しています。
シニアエンジニアによるコードレビューや、将来のプロダクション（実運用）移行を想定し、意図的な技術選定の「Why」と「トレードオフ（既知のボトルネック）」をここに開示します。

### 1. 技術選定のWhyとトレードオフ
* **Flutter Web × Firebaseの採用理由:**
  災害時における「アプリのインストール障壁（通信量と時間）」をゼロにするため、URL一発で起動するPWA（Progressive Web Apps）構造を選択しました。また、インフラや認証基盤の構築コストをゼロ化し、UI/UXの検証にリソースを集中させるためバックエンドにはFirebase（Firestore）を採用しています。
* **犠牲にした制約（既知の負債）:**
  Flutter Webの特性上、初回アクセス時に巨大なJavaScript（`main.dart.js`）をダウンロードする必要があり、極限の低速回線環境におけるファーストビューの起動速度に課題を残しています。実運用フェーズでは、初期ロードが圧倒的に軽量なNext.js（SSR）等へのフロントエンド刷新、またはネイティブアプリとしてのビルドをロードマップとして想定しています。

### 2. スケール時の物理的限界（ボトルネックと対策）
* **FinOps（無料枠）の破綻:**
  現状は全ユーザーがすべての要請データをリアルタイム同期（`snapshots()`）でリッスンする構造のため、ユーザー数・要請数が10倍になった時点でFirestoreのRead数が乗算で爆発し、無料枠が瞬時に枯渇します。
  * **対策:** 位置情報を「ジオハッシュ（Geohash）」に変換してドキュメントに持たせ、フロントからは特定のエリア（自分の周囲数キロメートル）のみをクエリする構造へ非正規化リファクタリングを行う必要があります。
* **空間クエリの限界:**
  Firestore単体では高度な地理空間演算（SQLの空間関数など）が行えないため、初期フェーズでは広域データを一度ブラウザ側にバルクダウンロードし、クライアント側のロジックで距離計算をしてフィルタリングしています。データ増大時は端末のメモリと通信帯域を圧迫するため、将来的には地理空間検索に強いPostgreSQL（PostGIS）などへデータアクセス層を移行する設計の抽象化が必要です。

### 3. 災害オフライン環境へのアプローチとUIハック
災害時の「完全オフライン（基地局ダウン）」環境に対して、本システムは以下の2段階のアプローチを想定・設計しています。

* **データフローの担保（Firebaseの標準機能）:**
  Firestoreの「オフラインデータ永続化（Offline Persistence）」を利用し、オフライン時の要請はブラウザのローカルキャッシュ（IndexedDB等）に一時保持され、端末が少しでも電波圏内に入った瞬間にバックグラウンドで自動同期されます。
* **ブラウザの制約（シークレットモード等）へのUXハック:**
  ブラウザのシークレットモード等ではローカルキャッシュが強制消去されるリスクがあります。これに対し、高度な通信プロトコル（Bluetooth P2P等）を複雑に組み込むのではなく、フロントエンドのUI/UXによる以下の「シンプルな代替案」を設計思想として持っています。
  1. **状態の可視化:** 未送信キャッシュがある場合、画面を閉じるとデータが消滅する旨を強力に警告するUIイベントのフック。
  2. **QRコードによるアナログ・バトンリレー:** 送信失敗時に要請内容（位置・ニーズ）をその場でQRコード化して画面に表示。電波が繋がっている他者の端末でそれを読み取ってもらい、代理送信（プロキシ）を依頼する。インフラの根本解決に依存せず、フロントの知恵で要請を届ける割り切りです。

### 4. AI協調開発（ペアプログラミング）のプロセス
開発プロセスにおいて、LLM（大規模言語モデル）を「リアルタイムで並走するシニアペアプログラマー」として定義しました。
Firebaseのセキュリティルール設計や、エッジケースにおける同時実行制御（Transactionsを用いた楽観的ロックの検討など）の壁打ち相手として徹底的に使い倒しています。AIの提示する理想的なアーキテクチャ（Cloud Functionsの多用など）を鵜呑みにせず、現場のデプロイ速度と運用のシンプルさを天秤にかけ、自らの意思でトレードオフを決定する「AIネイティブな開発プロセス」を実践しました。
