# ResQGo (災害救助支援デリバリーアプリ)
稼働URL: https://gms.gdl.jp/~reosato/disaster-delivery/

サポーターズ・技育CAMPハッカソンにて開発・本番デプロイを完遂した、被災者のリアルタイムなニーズとボランティアの最適な救助経路をマッチングするモバイルアプリケーションです。

## 🚀 プロダクトの核 (Why・How・Fact)

###  【Why】解決する課題
災害発生時における「避難所単位」の大まかな物資配分ではなく、**孤立した被災者個人の「今、水が必要」「持病の薬が足りない」といったピンポイントな微細ニーズが可視化されない**という課題を解決します。リアルタイムに位置情報と紐づいた需要をマップ上にプロットし、動けるボランティアへ最適な救助ルートを提案します。

###  【How】技術選定と開発プロセス
* **Frontend:** Flutter (Dart) によるクロスプラットフォーム開発。タイムクリティカルな状況での直感的なUI/UXを実装。
* **Backend:** Firebase (Firestore / Authentication) を採用し、NoSQLによるリアルタイムなデータ同期基盤を高速に構築。
* **AI-Driven Development:** 限られたハッカソンの時間制限の中で、LLM（大規模言語モデル）を単なるテキストジェネレータではなく**「リアルタイムで並走するペアプログラマー」**として定義。アーキテクチャの壁打ち、Firebaseのセキュリティルール設計、エッジケースの即時デバッグに徹底的に使い倒すことで、開発速度とロジックの安全性を両立させました。

###  【Fact】客観的成果
* 技育CAMPハッカソンにて、限られた時間制限の中でフロントエンドからバックエンドのインフラ統合、および本番環境へのデプロイ（デモ稼働可能な状態）までを完全ワンオペで完遂。

## 🧠 未来の自分への設計メモ（面接対策用Why＆カウンター一覧）

数ヶ月後の自分が「設計の割り切り」を10秒で思い出すためのカンペ。

### 1. なぜ Flutter Web × Firebase（PWA）なのか？
* **Why:** 災害時にストア経由のDLを排除し、「URL一発で即起動」させるため。ハッカソンでの技術的挑戦（突破力の証明）という戦略的側面もある。
* **トレードオフ:** 初回ロード時のJS（`main.dart.js`）が重く、極限の低速回線で起動が遅れるリスク。将来はNext.js（SSR）化かネイティブアプリ化が必要。

### 2. ユーザーが10倍になったらどこが壊れるか？
* **FinOpsの破綻:** 全件リアルタイム同期（`snapshots()`）のため、Read数が爆発し無料枠が秒速で枯渇する。
  * *対策:* 位置情報を「ジオハッシュ」に変換し、周辺エリアのみを絞り込んでリッスンする構造へ変更。
* **空間クエリの限界:** Firestoreは半径○kmの計算ができないため、全データをブラウザにバルクDLしてアプリ側で距離計算している。データ増大で通信とメモリがクラッシュする。
  * *対策:* 地理空間検索に強いPostgreSQL（PostGIS）等への移行。

### 3. 完全オフラインへの対策とUIハック
* **標準機能:** Firestoreの「オフラインデータ永続化」でキャッシュされ、電波復帰時に自動同期。
* **シークレットモード等のキャッシュ消滅リスクへのUXハック:**
  1. *警告UI:* ブラウザを閉じようとしたら「データが消滅します」と警告して画面保持を促す。
  2. *QRバトンリレー:* 送信失敗時に要請内容を「QRコード」化。電波が繋がっている他人のスマホに読み取ってもらい代理送信（プロキシ）を依頼。複雑なP2P通信を書かない割り切り。

### 4. AI（LLM）との協調・意思決定
* 重複を避ける排他制御について、AIはCloud Functionsでの実装を提案。しかし時間制約を考慮し、サーバーサイドを増やさず、クライアント側からFirestoreの `runTransaction()` を用いた楽観的ロックに留める判断を自ら下した。速度を最優先したトレードオフの証明。
